1. What is physically inside a GPU server?

Before jargon, picture the parts and where the data lives.

general-purpose brain
SYSTEM RAM — attached to CPU

CPU

Physically: the normal processor. It runs Linux, networking, tokenization, the inference server, scheduling, file I/O.

It coordinates; it is usually not where the giant model does its heavy matrix math.

System RAM

Physically: DIMMs next to the CPU. Big capacity, but much farther/slower for a GPU than its local memory.

GPU + HBM / VRAM

Physically: the AI compute chip plus very fast local memory. Model weights and KV cache ideally stay here.

Important: 1 TB of CPU RAM is not equivalent to 1 TB of GPU VRAM. You can sometimes offload model data to CPU RAM, but every transfer across the slower connection can hurt inference speed.

2. PCIe, NVLink, NVSwitch: they are roads for data

The easiest way to understand them is not as “AI technologies,” but as different roads connecting pieces of hardware.

🛣️

PCIe

The standard motherboard highway.

PCI Express connects GPUs, SSDs, network cards and CPUs. “x16” means 16 lanes. A PCIe 5.0 ×16 link carries about 63 GB/s in one direction after encoding overhead.

GPU peer-to-peer transfers can sometimes travel over PCIe without copying through CPU memory; topology and software support matter.

🚄

NVLink

A dedicated high-speed GPU link.

NVIDIA's high-bandwidth interconnect for GPU↔GPU (and some chip-to-chip) traffic. On H200 SXM, NVIDIA specifies up to 900 GB/s bidirectional NVLink.

NVLink does not magically fuse eight GPU memories into one ordinary RAM stick. Software still decides how the model is sharded.

🚦

NVSwitch

The switchboard connecting many NVLinks.

A high-bandwidth switch fabric. Instead of wiring only GPU A↔B, it lets many GPUs communicate through a shared high-speed fabric.

This becomes valuable for tensor parallelism and MoE expert traffic where GPUs exchange data constantly.

What is SXM, then?

PCIe card and SXM describe packaging/form factor, not the same thing as PCIe vs NVLink. A normal workstation GPU looks like an add-in card plugged into a PCIe slot. High-end H100/H200/B200 systems often use SXM GPU modules mounted onto a special baseboard, enabling high power delivery and dense NVLink/NVSwitch connectivity.

The main risks are… ▌

The UI can begin displaying the answer before all 300 output tokens have been generated.

2,000 input tokens → processed together

The server pushes a block of prompt tokens through the model. GPUs can use large matrix operations efficiently, so this phase has more parallelism.

prompt tokens → all model layers → build KV cache → first-token logits

Common pressure: compute, attention work, memory capacity. Very long prompts increase work and KV-cache demand.

300 output tokens → 300 sequential steps

To generate output token #2, the model needs token #1. To generate #3, it needs #2. That dependency makes generation fundamentally sequential within one sequence.

token 1 → token 2 → token 3 → … → token 300

Common pressure: reading model weights fast enough, GPU-to-GPU communication, and serving many sequences together efficiently.

Those selected experts are not necessarily on the same GPU. If experts are distributed across GPUs, token activations must be routed to the GPU that owns each expert and returned afterward. This is why interconnect can become a real bottleneck.

Capacity: does the model fit?

Current vLLM recipe lists the native FP8 V3.2 checkpoint at roughly 805 GB.

~805 GB model~323 GB remainder

8× H200 = 8 × 141 GB = 1,128 GB HBM.

1,128 GB − 805 GB ≈ 323 GB before runtime/cache details

That 323 GB is not all “free KV cache”: runtime workspaces, allocator behavior and other buffers also consume memory.

The inference engine shards weights and/or experts. The current vLLM guidance for V3.2 discusses tensor parallelism, data parallelism, and expert parallelism; for Hopper-class GPUs it specifically recommends testing DP/EP-style serving because V3.2's sparse-attention kernels can make naïve TP=8 inefficient.

Advanced: TP, DP, EP in plain English

TP — Tensor Parallel: several GPUs cooperate on the same matrix operation. Lots of synchronization.

DP — Data Parallel: different request batches are handled in parallel. Less cross-GPU coordination for each request, depending on model layout.

EP — Expert Parallel: different MoE experts live on different GPUs. Tokens are dispatched to the GPUs owning the chosen experts, then results are combined.

5. “Per input token” vs “per output token” in real life

There are two meanings: hardware work and API billing. They are related, but not the same.

Hardware view

Many prompt tokens can be processed in parallel. Long context increases attention/KV work.

OUTPUT TOKEN

One new token requires another pass through the network; a single conversation generates sequentially.

Why output often feels expensive: a 300-token response means roughly 300 decode iterations, while the server has fewer opportunities for parallelism within that one user's sequence.

Why batching changes economics

One user at a time may leave GPU compute underused. Serving engines such as vLLM use continuous batching: while User A is generating, tokens from Users B/C/D can share GPU execution.

low concurrency → better individual latency, worse utilization
higher batching → better total tokens/s, possible latency trade-off

API billing: a separate layer

Hosted providers usually charge by counted tokens. As of 2026‑09‑30, DeepSeek's published V4.1 Flash off‑peak rates are $0.15/M uncached input tokens and $0.60/M output tokens; cache-hit input is $0.003/M.

6. What becomes the bottleneck?

There is no single answer. Change the workload and the limiting resource moves.

VRAM capacity
medium
HBM bandwidth
high
GPU compute
medium
GPU↔GPU link
medium-high
KV cache
low
Low-batch decode: repeatedly touching model/expert weights makes memory bandwidth important. MoE also creates cross-GPU expert traffic.

Capacity bottleneck

Symptom: model cannot load, or context must be tiny.

Fix: more VRAM, smaller/quantized model, KV quantization/offload.

Bandwidth bottleneck

Symptom: GPU compute units wait for weights/data.

Fix: faster HBM, better batching/data reuse, optimized kernels.

Interconnect bottleneck

Symptom: GPUs wait on other GPUs.

Fix: NVLink/NVSwitch, better parallel layout, reduce communication.

Compute bottleneck

Symptom: tensor cores saturated.

Fix: lower precision, better kernels, more GPUs / more compute.

KV-cache bottleneck

Symptom: long context or concurrency runs out of VRAM.

Fix: FP8 KV cache, prefix caching, shorter contexts, more memory.

Scheduler bottleneck

Symptom: poor throughput or long queues despite hardware.

Fix: batching/scheduler tuning and workload-aware serving.

7. One subtle but important point: “8 GPUs” can mean two very different things

Case A — one giant model spans 8 GPUs

The GPUs must communicate during a request.

GPU 1 ⇄ GPU 2 ⇄ … ⇄ GPU 8

Interconnect matters a lot. Tensor/expert parallelism can exchange data repeatedly.

Case B — 8 independent model replicas

Each GPU/server can serve different users with little coordination.

User A → GPU 1
User B → GPU 2
User C → GPU 3 …

Interconnect matters less for the model's forward pass; capacity per replica becomes the issue.

8. Beginner glossary — “what is it physically?”

Search a term. Each card gives the physical meaning, why it matters, and an analogy.

GPU

A massively parallel processor.
Runs the matrix operations used by neural networks.
Analogy: thousands of specialized workers doing similar math together.

CPU

The server's general-purpose processor.
Runs OS, network, tokenizer, scheduler, storage and orchestration.
Analogy: the operations manager.

VRAM / HBM

Memory physically close to the GPU.
Holds weights, activations and KV cache at very high bandwidth.
Analogy: the GPU's workbench — nearby tools are fastest to reach.

System RAM

Memory attached to the CPU.
Large but far slower for GPU access than local HBM.
Analogy: warehouse across town, not the workbench.

PCIe

A standard high-speed computer I/O bus.
Connects CPU, GPU, SSD and NIC; may carry GPU peer traffic.
Analogy: the motherboard's highway system.

NVLink

NVIDIA high-bandwidth interconnect.
Lets cooperating GPUs exchange tensors far faster than ordinary host I/O paths.
Analogy: an express train between factories.

NVSwitch

A switching fabric connecting multiple NVLink GPUs.
Enables dense many-to-many GPU communication.
Analogy: the central train interchange.

Parameter

A learned numeric value in the neural network.
Total parameters strongly affect model storage.
Analogy: one adjustable knob in a giant learned machine.

Token

A small unit of text represented as an integer ID.
Prompts and outputs are measured and processed in tokens.
Analogy: pieces on a conveyor belt.

Inference

Running a trained model to produce outputs.
This is what a production chatbot server does.
Analogy: operating the factory, not building it.

Prefill

Processing the input prompt before generation.
Creates attention state/KV cache and the first output distribution.
Analogy: reading all the case files before answering.

Decode

Autoregressively generating new tokens.
Each next token depends on what came before.
Analogy: writing a sentence word-piece by word-piece.

KV cache

Stored attention keys/values from earlier tokens.
Avoids recomputing the entire past on every output step, but consumes VRAM.
Analogy: notes kept open on the desk while continuing a conversation.

Quantization

Representing numbers with fewer bits.
Cuts weight/cache memory and often improves speed, with possible accuracy trade-offs.
Analogy: storing measurements with fewer decimal places.

MoE

Mixture of Experts: many expert sub-networks, only some selected per token.
Huge total capacity without executing every expert for every token.
Analogy: a hospital routes each case to selected specialists.

Batching

Executing work for multiple tokens/requests together.
Improves GPU utilization and total throughput.
Analogy: a bus carries many passengers per trip.

TTFT / latency

Time until the user sees the first generated token.
Determines how responsive the app feels.
Analogy: time until a restaurant serves the first dish.

Throughput

Total work completed per unit time.
Matters for serving many users economically.
Analogy: meals served per hour, not one diner's wait time.
